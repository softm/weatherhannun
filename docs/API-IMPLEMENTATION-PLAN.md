# 날씨한눈 API 구현 계획

- 기준일: 2026-11-01
- 적용 대상: 날씨한눈 웹 및 Android 앱
- 상태: 현시점 구현 기준안

## 1. 목표

날씨한눈은 국내에서는 기상청의 공식 자료를 중심으로 제공하고, 해외에서는 좌표 기반 상세 예보와 각국 기상기관의 공식 도시 예보를 함께 사용한다.

외부 API는 앱과 웹에서 직접 호출하지 않는다. Firebase 백엔드가 API 호출, 인증정보 보호, 캐시, 데이터 정규화, 장애 대응, 정확도 기록과 알림 판정을 담당한다.

## 2. 현시점 공급자 결정

| 우선순위 | 공급자 | 적용 범위 | 담당 정보 | 결정 |
|---:|---|---|---|---|
| 1 | 기상청 단기예보 API | 대한민국 | 동네별 시간 예보, 기온, 강수, 습도, 풍속, 하늘 상태 | 필수 적용 |
| 1 | 기상청 초단기실황·예보 | 대한민국 | 현재 상태와 단시간 강수·기온 변화 | 필수 적용 |
| 1 | 기상청 특보 | 대한민국 | 호우, 폭염, 한파, 강풍, 태풍 등 공식 특보 | 필수 적용 |
| 1 | MET Norway Locationforecast | 해외 | 좌표 기반 현재·시간별·주간 예보 | 필수 적용 |
| 1 | WMO WWIS | 해외 주요 도시 | 각국 기상기관이 제출한 공식 일별 도시 예보 | 필수 적용 |
| 2 | AirKorea | 대한민국 | 미세먼지, 초미세먼지, 통합대기환경지수 | 적용 |
| 2 | 기상청 중기예보 | 대한민국 | 3~10일 전망 | 적용 |
| 2 | KIM·ECMWF Open Data | 국내·해외 | 모델 비교, 장기 추세, 정확도 검증 | 2단계 적용 |
| 3 | 웨더아이 | 대한민국 중심 | 독자 보정예보, 생활 콘텐츠, 유료 백업 | 견적·샘플 검증 후 결정 |
| 보류 | Open-Meteo | 전 세계 | 좌표 기반 모델 예보 | 상업 서비스 이용조건 확정 전 신규 사용 중단 |
| 보류 | OpenWeatherMap | 전 세계 | 상용 종합예보 | 핵심 공급자 부족 시 재검토 |
| 제외 | AccuWeather | 전 세계 | 상용 종합예보 | 현 요금·정책 조건상 제외 |

## 3. 데이터 선택 원칙

| 기능 | 기본 공급자 | 보조·검증 | 사용자 표시 원칙 |
|---|---|---|---|
| 국내 현재 날씨 | 기상청 초단기실황 | 최근 관측값 | `기상청 실황`과 관측 시각 표시 |
| 국내 시간별 예보 | 기상청 초단기·단기예보 | KIM·ECMWF | 발표 시각과 예보 기준 시각 표시 |
| 국내 주간예보 | 기상청 중기예보 | KIM·ECMWF | 공식 전망을 우선 표시 |
| 국내 위험기상 | 기상청 특보 | 없음 | 일반 모델 예보보다 우선 표시 |
| 국내 대기질 | AirKorea | 없음 | 측정소와 측정 시각 표시 |
| 해외 현재·시간별 예보 | MET Norway | WMO WWIS | 좌표 기반 상세값 표시 |
| 해외 주요 도시 일별 예보 | WMO WWIS | MET Norway | `공식 도시 예보` 배지와 출처 표시 |
| 공급자 간 차이가 큰 경우 | 공식 기관 자료 우선 | 다른 공급자 값 비교 | 임의 평균을 만들지 않고 `예보 변동성 높음` 안내 |
| 공급자 장애·지연 | 마지막 정상 자료 | 대체 공급자 | 마지막 발표 시각과 지연 상태 표시 |

WMO WWIS는 주요 도시의 공식 일별 예보를 제공하지만 임의 GPS 좌표의 시간별 상세 예보를 대체하지 않는다. WWIS 자료는 `forecast.issueDate`가 변경된 경우에만 새 자료로 처리한다.

## 4. 전체 구조

```text
기상청 / AirKorea / MET Norway / WMO WWIS
                    │
                    ▼
          Firebase Scheduled Functions
          - 공급자별 수집기
          - 재시도와 호출 제한
          - 원본 응답 검사
                    │
                    ▼
          정규화·비교·변화 감지 계층
          - 공통 날씨 코드
          - 단위와 시간대 통일
          - 발표 시각·출처 보존
          - 예보 차이와 위험도 계산
                    │
                    ▼
             Firestore / Cache
          - 최신 정규화 자료
          - 마지막 정상 자료
          - 예보·관측 이력
                    │
             ┌──────┴──────┐
             ▼             ▼
         웹 애플리케이션   Android 앱
                           └─ FCM 알림
```

## 5. Firebase 워크플로우

| 작업명 | 실행 주기 | 처리 내용 |
|---|---:|---|
| `kma-nowcast-sync` | 10분 | 국내 초단기실황·초단기예보 수집 |
| `kma-village-sync` | 공식 발표 시각 후 | 단기예보 수집, 실패하면 10·20·40분 후 재시도 |
| `kma-midterm-sync` | 공식 발표 시각 후 | 3~10일 중기예보 수집 |
| `kma-warning-sync` | 5분 | 신규·변경·해제 특보 감지 |
| `airkorea-sync` | 30분 | 등록 지역의 대기질 갱신 |
| `metno-active-sync` | 30분 | 최근 활동 중인 해외 지역 갱신 |
| `metno-saved-sync` | 60분 | 사용자가 저장한 해외 지역 갱신 |
| `wwis-city-sync` | 60분 | `issueDate`와 콘텐츠 해시를 비교해 변경분만 저장 |
| `wwis-index-sync` | 하루 1회 | 도시 ID, 좌표, 국가, 제공기관 목록 동기화 |
| `forecast-verify` | 하루 1회 | 과거 예보와 실제 관측값 비교 |
| `notification-evaluate` | 데이터 변경 시 | 의미 있는 기상 변화만 FCM 알림으로 전송 |
| `stale-data-audit` | 30분 | 공급자 장애, 갱신 지연, 결측 감시 |

전체 WWIS 도시를 매시간 동시에 호출하지 않는다. 활성·저장 도시를 우선 갱신하고, 나머지는 여러 배치로 나누어 3~6시간 간격으로 분산 처리한다.

## 6. 공통 응답 계약

웹과 Android 앱은 공급자별 원본 형식을 직접 해석하지 않고 다음 공통 구조만 사용한다.

| 필드 | 내용 |
|---|---|
| `location` | 행정구역, 도시명, 국가, 위도·경도, 시간대 |
| `current` | 현재 기온, 체감온도, 습도, 풍속, 강수, 날씨 상태 |
| `hourly[]` | 시각별 기온, 강수확률·강수량, 습도, 풍속, 날씨 코드 |
| `daily[]` | 날짜별 최저·최고기온, 대표 날씨, 강수확률 |
| `airQuality` | PM10, PM2.5, 통합대기환경지수, 측정소 |
| `alerts[]` | 공식 특보, 영향 지역, 발표·해제 시각 |
| `officialForecast` | WMO 또는 해당 국가 기상기관의 공식 도시 예보 |
| `comparison` | 공급자별 차이와 검증 상태 |
| `source` | 공급자, 원자료 발표 시각, 수집 시각, 이용조건 표기 |
| `stale` | 최신성 기준 초과 여부와 마지막 정상 갱신 시각 |

원자료의 발표 시각과 Firebase 수집 시각은 반드시 별도로 저장한다. 워크플로우가 실행된 시각을 예보 발표 시각처럼 표시하지 않는다.

## 7. 캐시·장애·비용 통제

| 상황 | 처리 원칙 |
|---|---|
| 원자료가 이전과 동일함 | Firestore 쓰기와 알림 생략 |
| 일시적 호출 오류 | 지수 백오프로 최대 3회 재시도 |
| 공급자 장애 | 마지막 정상 자료 유지 및 지연 표시 |
| 일부 필드 결측 | 정상 필드를 유지하고 결측 필드는 명시적으로 비움 |
| 공급자 값 충돌 | 임의 평균 금지, 공식 자료 우선 및 차이 안내 |
| 호출량 증가 | 인접 좌표를 예보 격자로 묶고 동일 요청 캐시 |
| 알림 중복 | 지역·현상·공식 발표번호·발표 시각으로 중복 제거 |
| API 인증정보 | Firebase Secret Manager에 저장하고 클라이언트에 노출하지 않음 |

## 8. 정확도 검증

예보가 지나간 뒤 관측값과 비교할 수 있도록 공급자별 원본 예보를 이력으로 보존한다.

최소 평가 항목은 다음과 같다.

- 기온: MAE와 최대 오차
- 강수: 발생 적중률, 누락률, 오경보율
- 풍속: MAE와 강풍 임계값 적중 여부
- 날씨 상태: 맑음·구름·비·눈 분류 일치율
- 평가 구간: 지역, 계절, 예보 선행시간별 분리

단순 전체 평균 순위로 공급자를 고정하지 않는다. 국내·해외, 도시·산간·해안, 1시간·24시간·7일 예보별로 가장 신뢰할 수 있는 공급자를 판단한다.

## 9. 구현 순서

| 단계 | 구현 범위 | 완료 기준 |
|---:|---|---|
| 1 | Firebase 프록시와 공통 데이터 모델 | 앱·웹에 외부 API 키가 없고 동일 응답을 사용함 |
| 2 | 기상청 실황·초단기·단기·특보 | 국내 핵심 화면과 공식 특보 알림이 작동함 |
| 3 | MET Norway | 해외 좌표 기반 시간별 예보가 작동함 |
| 4 | WMO WWIS | 해외 주요 도시 공식 예보와 출처가 표시됨 |
| 5 | AirKorea | 국내 대기질 카드와 알림이 작동함 |
| 6 | 캐시·재시도·최신성 검사 | 장애 시 마지막 정상값과 지연 상태가 표시됨 |
| 7 | 예보·관측 이력과 정확도 계산 | 공급자별 오차가 매일 누적됨 |
| 8 | KIM·ECMWF 검증 파이프라인 | 지역·시간대별 신뢰도 분석이 가능함 |
| 9 | 웨더아이 평가 | 샘플의 정확도 개선이 계약 비용보다 클 때만 도입함 |

## 10. 출처·이용조건

- 기상청과 AirKorea 자료에는 각 공공데이터 이용조건에 맞는 출처를 표시한다.
- MET Norway는 요구되는 식별 가능한 `User-Agent`, 캐시 정책 및 출처 표시 조건을 준수한다.
- WMO WWIS는 원문을 정확히 재현하고 `WMO World Weather Information Service`와 해당 국가 기상기관을 표시한다.
- WWIS의 광고·구독 앱 내 상업적 재사용 범위는 운영 전 서면 확인한다.
- 웨더아이 홈페이지를 크롤링하거나 무단 재배포하지 않는다. 도입 시 별도 API 이용계약을 체결한다.
- 공급자별 이용조건과 표시문구는 배포 전 다시 검토하고 변경 이력을 남긴다.

## 12. 현시점 결론

초기 운영 조합은 **국내 기상청 + 국내 대기질 AirKorea + 해외 상세 MET Norway + 해외 공식 도시 예보 WMO WWIS**로 확정한다.

KIM과 ECMWF는 정확도 검증을 위한 2단계 기능으로 도입한다. 웨더아이는 유료 샘플이 실제 정확도와 콘텐츠 경쟁력을 개선하는지 검증한 뒤 결정한다. Open-Meteo, OpenWeatherMap, AccuWeather는 현시점 핵심 운영 경로에 포함하지 않는다.
